## 一、先给结论

| 问题 | 结论 |
| --- | --- |
| 哪个界面设计最好？ | **分开看**：排版气质 ReadAware 最好（衬线、纸色、宽留白），**设置信息架构 Wenku8 最好**（编号分节 + 一句解释 + 命名预设），**阅读页信息密度 Wenku8/Readest 更合适**。ReadAware 的交互范式（零 chrome、纯图标、设置深埋）已被用户实机否定，不采用。详见第十一节 |
| 用哪个做基础框架最省力？ | **已拍板：自建 MIT**（Tauri 2 + foliate-js + readium/css）。省力的部分是渲染内核——foliate-js 已含 EPUB/MOBI/FB2/CBZ/PDF、竖排与 RTL、分页与滚动、CFI；不省力的是书架、进度、标注、搜索、转换向导、锻造层与回滚，全部自己写。Readest / ReadAware / Koodo / Wenku8 只能读架构，**代码一行不能抄** |
| 界面样式 | **Readest + Koodo 结合**：Readest 的干净阅读区与克制排版，Koodo 的桌面级书架密度、分组、右键菜单；再叠 Wenku8 的设置信息架构（编号分节 + 一句解释 + 命名预设） |
| 两者矛盾吗？ | 不矛盾。**工程自建（MIT），界面学 Readest + Koodo，排版气质学 ReadAware，设置信息架构学 Wenku8，TTS 交互学 MultiTTS，编辑流程学 Calibre，老板键学月读** |
| 功能怎么"兼容"？ | 一套渲染内核 + 一套领域模型 + 一层"锻造覆盖层"。**借用只发生在设计与交互层**：AGPL（Readest/ReadAware/Koodo）与 GPL（Wenku8/Calibre）的代码一行不抄，只读架构后按 MIT 自写 |
| 最终效果一句话 | **界面像 Readest 一样干净、像 Koodo 一样好管理；既能读（横排/竖排、翻页/长页、彩页原色）、又能转（TXT→EPUB 向导）、还能改（写回源文件 + 可回滚）——一台桌面上的"阅读 + 锻造"工作台。** |
| 已定的其余四项 | 双模式切换（专注/工作台）、独立转换向导、写回源文件+回滚、TTS 默认系统语音可升级 |

> 本文件不写代码，只回答"选谁、借什么、最后长什么样"。

### 3.3 关键洞察

1. **"最好看"和"最适合当骨架"是两个问题。** ReadAware 赢在阅读面；Readest 赢在工作台与工程底座。
2. ReadAware 的阅读面优势是可以"抄感觉"的：字号阶、行高、页边距、工具栏显隐逻辑、进度药丸位置。这些是设计 token，不是架构，迁移成本低。
3. Readest 默认阅读面其实也干净（工具条可隐），它的"密"主要来自三栏与笔记本。我们 fork 后可以默认关掉侧栏/笔记本，把密度降下来。
4. Koodo 唯一值得抄的是**书架管理的信息架构**（分组、排序、右键菜单项），不是视觉。

## 五、技术栈与工程量对比

| 维度 | Readest | ReadAware | Koodo |
| --- | --- | --- | --- |
| 桌面壳 | Tauri 2.11 | Tauri 2 | Electron |
| 前端 | Next.js 16.4 + React 19.2 | Vite 7 + React 19.2 + TanStack Router + Jotai | React（旧架构） |
| 样式 | Tailwind v4 | Tailwind v4 + Storybook | — |
| 渲染内核 | foliate-js（workspace 工程化版） | vendored foliate-js（自维护分支） | 自研 |
| 后端 | Rust（SQLite/搜索/格式） | Rust（SQLite 事件日志/FTS/projections/插件沙箱） | Node/Electron |
| Windows 分发 | 安装包 + 文件关联 + 资源管理器缩略图 | 安装包（未签名，SmartScreen 提示） | 安装包 |
| 工程复杂度 | 较高（Next.js + 大 monorepo + 多平台） | 中等（Vite + 模块化 monorepo） | 中等 |
| 维护风险 | 低（≥100 贡献者，日更） | **高（1 贡献者）** | 低 |

### 5.1 两个容易被忽略但很关键的事实

1. **Readest 的中文 TXT 章节识别"有代码、会失败"**：`txt.ts` 的流程是"先按 8 个以上连续换行切成若干段 → 每段单独跑章节正则 → 每段至少要有 2 个非空片段才算有效"。《红楼梦》Gutenberg 版每章之间正好 8 个空行，于是切成 123 段、每段只有 1 个标题、全部判为无效，最终退化成"每 100 段落一个数字分块"。实测侧边栏目录就是 `1, 2, 3…`，页脚 `1 / 1965`。而《西游记》章间最多 183 个空行，跨段合并后能匹配 89 个标题，所以"看起来支持"。
   结论：**问题不在"支不支持中文"，在"先切段再匹配"这个顺序**。开场白模板 2 里"换成本项目已验证的 `第X章 + ---` 规则"应改为"**直接换掉这一层，移植逐行分类算法**"（见 10.3）。
2. **Readest 已有 Proofread 规则**：用户自定义正则/纯文本查找替换，作用域可选选区/本书/全库，作用对象可选"仅显示 / 仅 TTS / 两者"，且不改原文件。这正是"锻造覆盖层"的现成底座——我们只需要把它从"规则式替换"扩展成"段落级改写 + diff + 版本"。

### 5.2 结论

- **省力**：Readest。它的"阅读底座 + 显示层替换 + 中文 TXT"三件事已经落地，我们只需在它上面加锻造层。
- **好看**：ReadAware。但它的优势是设计语言，不是工程底座；单作者 + 10 个月版本，作为骨架的长期风险明显高于收益。
- **最干净**：自建（MIT），但要把书架、DB、搜索、标注、设置、进度、TTS、翻译、脚注、转换全部重写，工作量最大。

## 六、三条路线

### 路线 A（推荐）：fork Readest，视觉学 ReadAware

**减法**

- 移除云端同步、商店/订阅、遥测、更新检查地址（以仓库实际模块为准）
- 只保留 Windows 构建目标，裁掉 iOS/Android/macOS/Linux 构建脚本
- 替换品牌：app 名、标识符、图标、About、官网链接

**加法**

- 锻造层：选区菜单 → 改写/翻译/注释；右侧 diff 抽屉；确认后写入覆盖层；版本表 + 回滚
- 把 Proofread 的"仅显示"模式升级为"锻造覆盖层"（原文只读，改动全部落 SQLite）
- TXT→EPUB 导出（封面/目录/注释脚注）
- 老板键 / 透明窗口（Tauri 全局快捷键 + 窗口透明度）
- Phase 4：AI 摘要 + 跨书记忆（参考 ReadAware 的 Agent 工具契约，不搬代码）

**改**

- TXT 章节：**换掉 `txt.ts` 的"切段后再匹配"层**，移植 ReadAware 的逐行分类（第X章/卷一/楔子/前后言/纯数字可信度校验/书内目录去重），再补 Koodo 式的"每本书可切换解析器 + 大文件按需窗口扫描"
- UI 降噪（可选）：默认隐藏侧栏/笔记本、加大页边距、底部工具条改浮动胶囊

**风险**

- Next.js + 大 monorepo 上手成本；上游合并冲突；AGPL 传染
- 缓解：pin 一个 release tag、只改必要模块、把锻造层做成独立 feature 目录，减少与上游的交叉

### 路线 B：fork ReadAware，保留它的设计与 Agent 架构

**优势**

- 界面直接到位，无需换肤
- 事件溯源 + 工具注册表 + 插件沙箱，天然适合锻造层与 AI Agent
- Vite 工程比 Next.js 简单，代码库更小、更一致

**代价**

- 单作者项目，上游修复基本没有，等于自己接手维护
- v0.6.x，Windows 未签名，实际稳定性需实测
- 付费 AI/relay 同步模块要拆
- 仍然要自己写锻造层、TXT→EPUB、老板键

**适用条件**：你把"产品独特性 + 界面一致性"排在"上线稳定性"之前，并且愿意长期自己维护。

### 路线 C：自建骨架（MIT 干净路线）

`create-tauri-app` + foliate-js（MIT）+ readium/css（BSD-3），其余全自写。

**唯一优势**：许可证干净、完全掌控。
**代价**：阅读底座全部重写，工程量最大，且要重新踩一遍 Readest/ReadAware 已经踩过的坑。

**只有在"MIT 不可让步"时才选它。**

### 路线对比

| | 改动量 | 稳定性 | 界面最终效果 | 许可 | 适合 |
| --- | --- | --- | --- | --- | --- |
| A fork Readest | 中 | 高 | 好（需降噪） | AGPL | 想最快得到一个稳的成品 |
| B fork ReadAware | 中 | 中低 | 最好（原生） | AGPL | 想要独一无二的产品气质 |
| C 自建 | 大 | 中 | 完全可控 | MIT | 许可证必须干净 |

## 七、功能怎么"兼容"：一套模型 + 分层借用

### 7.1 四条硬规则

1. **一套渲染内核。** fork Readest 就用它自带的 foliate-js 工程化版；不要再接 epub.js 或 Readium，否则两套定位/分页会打架。
2. **一套状态与路由。** 不要同时保留 Next 与 Vite 两套工程；跨项目（Celstack）共享库只允许"参考写法、自己重写"，不能搬 AGPL 代码。
3. **原文只读，改动落覆盖层。** 所有锻造动作写 SQLite（原文 → 改后 → 版本），不回写书籍文件；导出时才生成新文件。Readest 的 Proofread "Apply to: Display / TTS-only" 已经证明这条路可行。
4. **定位统一用 CFI。** 段落级 locator = 章节 CFI + 块序号 + 字符偏移；TXT 用合成书 + 合成 CFI，保证改字号/改窗口后不跑位。

### 10.3 中文 TXT 章节识别：三套算法逐一复现（本节最重要）

| | Readest | ReadAware | Koodo |
| --- | --- | --- | --- |
| 算法顺序 | **先切段，再匹配**：按 `8 个以上连续换行` 或 `8 个以上连字符` 切段，每段单独跑正则，且要求每段 ≥2 个非空片段 | **逐行分类**，不切段；再对纯数字标题做可信度校验（首个 ≤2、严格递增、跨度 ≤ 数量×3）；再剔除书内目录堆叠 | **逐行判定**，不切段；行长 <50 字、剥掉 `- _ = +`、关键词表（章/节/回/卷/部/篇…）+ 前后言表；>10000 行时改为 ±3000 行窗口按需识别 |
| 《紅樓夢》 | 切成 **123 段**，每段仅 1 个标题 → 全部作废 → 回退"每 100 段落一块" | candidates 139 → **accepted 123**，首尾正确（第一回…第一二零回） | 逐行命中，预期 123（未跑完 UI，算法判定等价） |
| 《西遊記》 | 10 段 → 匹配 89 个标题（章间 183 空行导致跨段合并），**看似可用** | candidates 91 → **accepted 90** | 同上 |
| `chapter-rules.txt` | 1 段 → 8 个候选，段落数 1 → 失效 | candidates 10 → **accepted 9** | 规则覆盖 9 种 |
| 大文件 | 无窗口化；整本转换 | 分块 `CHUNK_CHARS=60_000` | **±3000 行窗口**，避免整本扫描 |
| 每本可换解析器 | ✗ | ✗ | **✓**（内置解析器 + 自定义正则，可按书覆盖） |

**结论（可直接写进设计文档）**

1. Readest 失败与"中文/繁简"无关，**根因是"先切段再匹配"**：切段阈值 8 个空行恰好撞上中文公版书的排版习惯。
2. 稳健做法是 **逐行分类**（ReadAware / Koodo 同构）。Scrollforge 直接移植 ReadAware 的 `splitTextIntoChapters`（含 `numberingIsCredible`、`dropContentsListing`）即可，约 260 行、纯函数、无依赖。
3. 再叠一层 **Koodo 的"每本书可切换解析器 + 大文件窗口化"**：前者解决"算法猜不准"，后者解决"10MB 启动卡"。
4. `---` 只是规则表里的一条，不是方案本体——开场白里"按 `第X章 + ---` 重写"的说法要整句改掉。

### 10.4 硬换行熔接：两边都没做（这才是真差异点）

- Readest `formatSegment` 按 `\n+` 逐行生成 `<p>`；ReadAware `linesToParagraphs` 每个非空行 = 一段。
- 结果：Gutenberg 中文 TXT 被排成"一句一行"的碎片段落，双栏分页下尤其明显（截图可见）。
- Scrollforge 可在此做出真实差异：**段落重排（去硬换行 / 首行缩进 / 对话行识别）**，属于纯文本预处理层，与渲染内核解耦。

### 11.5 产品定位修正：阅读器 + 编辑器

用户明确："TXT 识别不了不要紧，可以出格式转换，难点是转换经验和后续修改空间。" 于是定位改为：

- **读**：EPUB / TXT / MOBI / AZW3 / FB2 / CBZ / PDF 统一进同一套书架、进度、标注。
- **转**：TXT → EPUB 是**核心流程**，不是附属功能。资产是"经验"——章节算法、硬换行熔接、对话行识别、封面生成、脚注/注释映射、结构校验、可回滚的中间产物。
- **改**：原文只读，改动落在覆盖层（改写/翻译/注释），带 diff 预览与版本快照，可回滚、可导出。

因此界面上要有**三处入口**：书架（读）、导入/转换向导（转）、阅读页右侧"锻造"抽屉（改）。

## 十三、新增交互规格（第三轮补充，来自用户点名）

### 13.1 竖排与右到左（日文轻小说 / 中文古籍）

**可行性有据**：foliate-js 的 `paginator.js` 已按 `writing-mode` 分支（`getDirection` 判 `vertical-rl`/`vertical-lr`，`columnize` 里用 vertical 决定分页轴），所以竖排不是从零做，只需在 CSS 层给文档根设 writing-mode 并让翻页方向反转。

**三个独立开关，不要合成一个"RTL"**：

| 开关 | 取值 | 说明 |
| --- | --- | --- |
| 文字方向 | 横排（默认）/ 竖排 | 决定 `writing-mode` |
| 翻页方向 | 左→右 / 右→左 | 决定分页轴正负、双页顺序、进度条方向 |
| 自动识别 | 开 / 关 | 读 EPUB 的 `page-progression-direction="rtl"` 与 `lang="ja"`，命中时**提示一次**，不静默切换 |

**联动清单（少做一项就会"看着别扭"）**：双页左右顺序、进度条方向、`←/→` 键语义反转、目录缩进方向、书签缩略图朝向、朗读推进顺序、"下一页"手势方向。

**竖排细节**：`<ruby>` 注音、标点挤压、西文与数字直立、破折号/长音符旋转、行距与字距、插图朝向。

**命名预设（直接可用）**：`现代中文·横排左→右`、`日文轻小说·竖排右→左`、`中文古籍·竖排右→左`。

### 13.2 翻页与滚动模式：做成可组合矩阵，不做单一开关

| 阅读模式 | 表现 | 成本 |
| --- | --- | --- |
| 平移翻页 | 整页横向滑入（最常用） | 低 |
| 覆盖翻页 | 新页从侧面盖住旧页 | 低 |
| 淡入淡出 | 旧页淡出、新页淡入 | 低 |
| 瞬时切换 | 无动画，最省电 | 低 |
| 双页跨页 | 左右双页，含单页↔双页一键切换 | 中 |
| 连续纵向滚动 | 长页一直往下滚 | 低（foliate `scrolled`） |
| 连续横向滚动 | 长页左右滚动 | 中 |
| 缩放 / 固定版式 | FXL 与画册，用缩放而非重排 | 中 |
| 卷页（curl） | 纸张卷曲动画 | **高，列为 P2 可选** |

组合规则：**阅读模式 × 动画 × 分栏（单栏/双栏/自动）** 三轴独立；每个组合都进"预设"，用户不必自己拼。

### 13.3 彩页与固定版式 EPUB

| 问题 | 方案 |
| --- | --- |
| 彩图被主题染色 | 三档策略：**保持原色（默认）/ 融入纸色 / 夜间柔化** |
| 识别彩页 | `properties="cover-image"`、`rendition:layout=pre-paginated`、单页图片占屏比超阈值 |
| 排版冲突 | 彩页**单独成页**，不与正文混排；可点开全屏、可从缩略图跳转 |
| 固定版式书 | 整页渲染、禁用重排、字号不生效，改由 Ctrl+滚轮缩放 |

### 13.5 内置说明书（离线）

- **入口**：`F1`、菜单"帮助 → 使用说明"、空书架卡片、首次启动引导。
- **内容**：5 分钟上手、快捷键表（**从命令注册表自动生成**，避免文档与实现不一致）、每个设置项一句人话解释、格式支持矩阵、常见问题。
- **形态**：Markdown/HTML 打包进 app，可搜索；每条带"在界面中高亮这个按钮"的指引，解决"知道有功能却找不到"。

### 13.6 写回源文件与回滚（决策 4 的落地规格）

- **保存链**：写临时文件 → 校验（EPUB 结构 / TXT 编码）→ 原子替换 → 原文件移入 `.history/<bookId>/<rev>`，保留 N 份。
- **revision**：每次保存记录时间、摘要、diff；历史面板可看 diff、可一键回滚；**回滚本身也生成新 revision**（永不丢历史）。
- **格式差异**：TXT 保持原编码与换行风格；EPUB 用 zip 重打包，`mimetype` 必须第一个条目且不压缩。
- **防损坏**：写前加锁、检测外部修改（mtime + hash）、失败自动回退。

### 13.7 双模式的具体差异（决策 2 的落地）

| 顶部 | 细条（32px）：书名、章节、页码、模式 | 完整工具栏：导入、转换、搜索、标注、设置 |
| 切换 | `F11` 或右上角"专注/工作台"双态按钮 | 同上 |

## 十四、ReadAware 插件截图逐项解释（用户上传截图）

**这张图在讲什么**：设置弹窗，左侧是导航（通用 / 阅读 / AI / 插件 / 主题 / 自定义 / 快捷键 / 数据与同步 / 关于），下面还挂着 6 个**由插件注入**的条目：`Image Backgro…`（背景图）、`RSS Reader`（订阅源）、`Sentence Reader`（句子阅读）、`TTS Voices`（音色）。右侧是"插件"页。

**顶部提示语**："插件与应用运行在同一个环境，拥有与应用相同的数据访问能力。请只安装你信任的插件。"——也就是说，它的插件是**同权限原生模块**，不是沙箱；这也解释了为什么它能改主题、能查词典、能接管 TTS。

| 条目 | 中文解释 | 那几个小按钮是什么 |
| --- | --- | --- |
| **Dictionary v1.4.0（内置）** | 阅读时选中单词查释义、保存生词，并在可搜索的时间线里回顾全部查词记录 | `读取阅读记录` / `读取整库` / `AI 请求` / `Agent 工具` 是**授权范围**，不是功能按钮。当前授权：全部书籍 |
| **Editorial Themes v1.0.0（内置）** | 两套排版主题：**Gutenberg**（做旧纸的浅色）、**Nocturne**（安静的墨蓝深色），正文用 EB Garamond 字体 | 同上，授权"修改书籍访问" |

| `RSS Reader` | RSS 订阅源阅读 | 同上 |
| `Sentence Reader` | 按句阅读/逐句高亮 | 同上 |

**我们要改的三处**

1. **不照搬"插件系统"**：改成"功能模块开关"——中文名 + 一句话说明 + 授权范围下拉；"插件市场 / 从 zip 安装"放进 P2 再议。
2. **插件设置不塞进主导航**：截图里 `Image Backgro…` 被截断，正是"英文长名 + 复用导航"的直接后果。这些应归入"设置 → 扩展功能"里的二级列表。
3. **授权要可见但别喧宾夺主**：默认"仅当前书籍"，用户点开才看到"读取整库/AI 请求"这类范围声明。
