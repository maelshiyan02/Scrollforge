# 04 — 三档数据分层与锻造双文档架构（含文件级操作、阅读撤销栈）

日期：2026-11-11
状态：**主要方向已拍板（2026-11-11）；S5–S13 全部完成**（S13 于 2026-11-14 收口，双文档渲染评估后暂缓）
前置：`03-编辑器布局与目录概念拆分-20261109.md`（S1–S4 已完成）

## 0. 一句话结论

你的三层设想与现状**大方向一致**：阅读层已经是"壳"（划词译文落在书目录 JSON），编辑层已经直接改原文件，锻造层已经有"译文只进草稿"的段级双栏。但有 **4 处硬偏差**必须先修正认知，否则后面的文件级操作和双文档会建在错的地基上：

1. **阅读层只有一半是壳文件**：划词译文在 `translate-drafts.json`，但高亮/笔记仍在 `localStorage`，清缓存即丢、换机不跟书。
2. **锻造的"保存"仍会改原文**：`commit_forge` 把改写结果写回 `source.txt`；且 EPUB 书**根本没有可写路径**（`epubFlatBlocks` / `epubOutputPath` 传进 ForgePanel 后未被使用），点保存会报"找不到这本书的源文件"。
3. **锻造已有"段对双栏 + 整章对照 + 段落撤销栈"**，但这是"段落对"，不是"原文文档 / 译文文档"两套渲染；也没有独立的译文文件实体。
4. **阅读层没有任何撤销栈**：高亮、笔记、划词译文都不可撤销。

## 1. 把你的设想翻译成可执行模型

### 1.1 三层数据模型

| 层 | 名称 | 内容 | 谁写 | 是否碰原书 |
| --- | --- | --- | --- | --- |
| L0 | 母本 | `source.epub` / `source.txt` | 仅编辑档（锻造的"合并回原文"是显式例外） | 是 |
| L1 | 阅读壳（sidecar） | 高亮、笔记、阅读进度、划词译文、阅读设置快照 | 阅读档 | 否 |
| L2 | 译文工程 | 逐章译文（XHTML 或 blocks JSON）+ 原文↔译文映射 + 可导出的 `translation.epub` | 锻造档 | 否 |

**三档写权限**（建议作为硬约束写进代码注释与类型）：

- 阅读档：只写 L1；禁止写 L0/L2。
- 编辑档：只写 L0；禁止写 L1/L2（阅读标注不因编辑而消失，但编辑档不提供标注 UI）。
- 锻造档：只写 L2；**不写 L0**。"合并回原文"是独立按钮 + 预览 diff，不属于常态保存。

### 1.2 三条不变式

1. **母本不可被阅读/锻造静默修改**：任何写 L0 的动作都必须有显式入口、变更预览、可回滚版本。
2. **锚点必须能降级**：CFI 在母本被编辑后会漂移，所有 L1/L2 数据除 CFI 外必须同时存 `href + blockIndex + textHash + 前后引文`，定位失败时按文本兜底并标记"待复核"。
3. **每个 sidecar 文件必须带** `schemaVersion`、`bookId`、`sourceFingerprint`（母本 hash）、`updatedAt`；指纹不一致时只读展示并提示"母本已变更"。

## 3. 可行性评估

### 3.1 阅读层壳文件统一（高可行）

- `translate-drafts.json` 的落盘模式可直接复用：新增 `read_sidecar` / `write_sidecar` 通用命令，`annotations` 从 localStorage 迁入 `sidecar/annotations.json`。
- 迁移策略：首读时若文件不存在而 localStorage 有数据，一次性升格写盘并保留 localStorage 作为降级副本。
- 风险：并发写（多窗口）→ 用"临时文件 + rename"原子写；写入失败保留内存态并提示。

### 3.2 阅读层撤销栈（高可行）

- ForgePanel 的 per-target 栈已验证可行（40 步、1.2s 合并、Ctrl+Z）。
- 阅读层建议统一为 `UndoStack<Annotation | Draft>`，按 `targetKey`（`annotationId` / `cfi`）分栈；持久化最近 20 步到 sidecar，跨会话可撤销。
- 范围建议：划词译文 + 高亮 + 笔记 三者统一入口；删除标注也可撤销。

### 3.3 编辑层文件级增删改移（中高，最大工程量）

必须同步的 5 类引用：

1. OPF `manifest`：新增/删除 `item`（id、href、media-type、properties）。
2. OPF `spine`：`itemref idref` 增删与顺序。
3. `nav.xhtml`：目录项 href 与文本。
4. `toc.ncx`：`navPoint` 的 `src` 与 playOrder（若存在）。
5. 书内相对链接：其他章节/注释里指向被重命名文件的 `href`。

风险与对策：

- **事务化**：先在临时目录完成全部改写，`edit_validate` 通过后一次性替换；失败回滚。
- **id 生成**：新文件 id 用 `file-<slug>-<n>`，避免与既有冲突；重命名保持 id 不变（只改 href）。
- **移动**：改 href 前先算相对路径（OPF 目录 vs 文件目录），并同步所有引用方。
- **删除**：若文件在 spine 中且是唯一正文，禁止直接删；要求先确认并自动从 nav/ncx 摘除。
- **校验**：复用现有 `edit_validate`（mimetype/container/OPF 可解析/spine 全在 manifest/brokenLinks）。

### 3.4 锻造双文档与分屏（中高，建议分两步）

- **轻模式（先做）**：译文以"逐章 XHTML"落在 `translation/`，由现有 `epub-writer` / 编辑打包能力导出 `translation.epub`。分屏仍是段对双栏，但两侧数据源分开（左母本只读、右译文工程），并支持整章成对滚动。
- **重模式（后做）**：左窗格用 foliate 渲染母本、右窗格渲染译文 XHTML，双实例独立滚动 + 按 `blockIndex` 同步定位。需要评估双实例内存与 CFI 同步成本。
- **不建议**直接维护"第二本完整 EPUB"作为工作文件：每次改一段都要重打包全部资源，冲突与体积代价高；译文工程目录 + 导出产物更稳。

### 3.5 导出译文 EPUB（中）

- 复用编辑档的解包/打包链路：复制母本资源与样式，替换正文 XHTML 为译文，重写 OPF/spine/nav 标题为译文，保留图片与字体。
- 需要在导出前做完整性检查：未翻译段落数、空译文、block 对齐漂移。

## 4. 预期与现状的差异（需要你确认的认知修正）

1. **"锻造绝不碰原文件"目前不成立**：`commit_forge` 会写 `source.txt`，且 EPUB 保存路径未接。要么把"改写"移出锻造，要么把保存改成"只写译文层 + 显式合并"。
2. **"阅读层都是壳文件"目前只成立一半**：高亮/笔记还在 localStorage。
3. **"原文与译文是两个文件"目前不成立**：只有一个 `forge-draft.json` 镜像文本，无法独立打开、校对、导出。
4. **"分屏"目前是段对双栏**：阅读体验上像分屏，但本质是一段原文 + 一段译文输入框，不是两份文档各自渲染。
5. **锚点稳定性**：编辑档一旦增删段落，`forge-draft.json` 与 `translate-drafts.json` 的 index/CFI 会错位，当前没有 `sourceFingerprint` 校验，也不会提示。

## 5. 改动方向

### 5.1 统一 sidecar

```
app-data/<bookId>/
  source.epub / source.txt        # L0 母本
  sidecar/
    manifest.json                 # schemaVersion / sourceFingerprint / 各文件索引
    annotations.json              # 高亮 + 笔记 + 颜色
    reading.json                  # 进度、阅读设置快照（可选）
    translate-drafts.json         # 划词译文（从书根迁入）
  translation/                    # L2 译文工程
    mapping.json                  # chapterId / blockIndex / sourceHash / href
    chapters/<id>.xhtml           # 逐章译文
  forge-draft.json                # 过渡期保留，后续并入 translation/
  revisions/                      # 母本版本（编辑/合并回原文）
```

### 5.2 统一锚点

```ts
type Anchor = {
  cfi?: string
  href?: string
  blockIndex?: number
  textHash: string      // 原文片段归一化后的 hash
  quote: { before: string; exact: string; after: string }
}
```

定位顺序：CFI → href+blockIndex → textHash → quote 模糊匹配；失败则标 `orphan` 并在标注面板集中提示。

### 5.3 编辑文件操作走"引用索引"

新增 Rust 命令族：`edit_file_create / rename / delete / move`，内部统一：

```
扫描 OPF(manifest/spine) + nav + ncx + 全包 href
  → 生成变更计划（diff）
  → 应用到临时工作目录
  → edit_validate
  → 提交并生成 revision
```

前端文件树加右键菜单/工具栏，操作前弹"影响 N 处引用"的确认。

### 5.4 锻造拆通道

- `translate`：只写 `translation/chapters/*.xhtml` + `mapping.json`，绝不碰 L0。
- `rewrite`：从锻造档移除，归编辑档（段落视图已有改写能力）；如保留，必须走"合并回原文"显式动作 + diff 预览 + revision。
- `AI 润色`：只作用于译文，已符合。

### 5.5 撤销栈统一

`lib/undo-stack.ts`：通用 per-target 栈（深度、合并窗口、持久化 key 可配）；锻造译文、阅读译文、高亮、笔记共用；`Ctrl+Z` / `Ctrl+Shift+Z` 在对应输入区生效，非输入区回退最近一次标注操作。

### 9.2 为什么不建顶层"壳数据"文件夹

- 壳数据要和原书一起移动：放在 `local book repository/<书目录>/` 内，复制/搬移书目录即可整体带走。
- 顶层独立文件夹必然需要一张"壳文件 ↔ 原书"映射表；表丢了两边就对不上，正是你担心的"记录丢失"。
- 折中：数据放书目录内，`local book repository/library-index.json` 只存索引（可随时扫目录重建）。

### 9.3 修订后的目录结构（可读命名）

```text
local book repository/
  library-index.json                    # 索引：id / 目录名 / 书名 / 源文件名 / 指纹 / 壳文件版本 / 自检时间
  <书名>__<短ID>/                        # 例：轮回第7次__a3f9（书名可读，短ID 保唯一）
    meta.json                           # 含 id、dirName、sourceName、sourceFingerprint
    source.epub                         # L0 母本（保留源扩展名）
    阅读壳/
      <书名>.标注.json                   # 高亮 + 笔记 + 颜色 + 锚点
      <书名>.划词译文.json               # 划词翻译草稿
      reading.json                      # 进度与阅读设置快照（可选）
    译文/
      mapping.json                      # 章节/段落/原文 hash/译文文件 对应
      章节/
        第01章-<章节标题>.xhtml
        第02章-<章节标题>.xhtml
    版本/                                # 编辑与"合并回原文"的 revision
  _external/                            # 历史模式（只登记外部路径）的书
    <书名>__<路径短哈希>/
      阅读壳/ ...
```

命名规则：

- 书名、章节名做 Windows 非法字符清洗（`\ / : * ? " < > |` → `_`，去掉结尾空格与点）。
- 短 ID 只用于消歧和稳定引用，**不展示给用户**；展示层始终用书名/章节名。
- 同一书名重复导入时用 `__a3f9`、`__b7c1` 区分，不出现 `1`、`2` 这种无意义后缀。
- 章节文件名带序号前缀，保证资源管理器里按阅读顺序排列。

### 9.4 索引与自检（解决"记录不要丢失"）

`library-index.json` 字段：

```json
{
  "schemaVersion": 1,
  "updatedAt": 0,
  "books": [
    {
      "id": "a3f9",
      "dirName": "轮回第7次__a3f9",
      "title": "轮回第7次",
      "sourceName": "轮回第7次.epub",
      "sourceFingerprint": "sha256:...",
      "sidecar": { "annotations": 1, "reading": 1, "translateDrafts": 1 },
      "translation": { "mapping": 1, "chapters": 14 },
      "lastCheckedAt": 0
    }
  ]
}
```

规则：

- 索引缺失或损坏 → 扫描书目录下的 `meta.json` 自动重建，不阻塞阅读。
- 启动时做轻量核对：索引有而目录无 → 标记 `missingDir`；目录有而索引无 → 自动补录；`sourceFingerprint` 不一致 → 标 `sourceChanged`，壳数据转只读并提示。
- 设置页提供"检查书库"按钮，输出三类结果：正常 / 可修复 / 需人工处理。

### 9.5 迁移策略（现有数字目录）

1. 扫描 `local book repository/` 下所有含 `meta.json` 的数字目录。
2. 按 `title` + `sourceName` 生成可读目录名，冲突加短 ID。
3. **目录重命名，id 保持不变**（id 仍存在 `meta.json`，所有命令通过索引解析 `id → dirName`）。
4. 旧路径引用（进度、封面缓存、`translate-drafts.json`、`forge-draft.json`）随目录一起移动，逻辑路径不变。
5. 迁移失败单本回滚，不整体中断；迁移结果写入索引 `lastMigratedAt`。

风险：`book_dir(app, id)` 目前是 `books_root.join(id)` 的直接拼接，改为"先查索引、再扫 `meta.json` 兜底"；所有 Rust 命令统一走一个 `resolve_book_dir()`，避免遗漏。

### 9.6 锻造译文与导出

## 10. 阅读标注与编辑档的关联规则（2026-11-11 拍板）

### 10.1 三档可见性与写权限

| 档位 | 母本 | 阅读标注 | 说明 |
| --- | --- | --- | --- |
| 阅读 | 只读 | 可读可写 | 标注存 `阅读壳/`，不碰母本 |
| 锻造 | 只读（左半屏） | 可见、可编辑均不影响 | 锻造不改原文，标注无风险 |
| 编辑 | 可写 | 富文本可见可编辑；源码不可见 | 改写/删除会连带影响标注，见下 |

### 10.2 标注粒度重构（关键变更）

| 类型 | 旧粒度 | 新规则 |
| --- | --- | --- |
| 笔记 | 任意选区（含几个词） | **只能挂段落或标题**（block 级） |
| 高亮 / 下划线 / 划词译文 | 字符偏移 | 保留字符级锚点，但与所属 block 绑定 |

理由：段落级笔记不会因为段落内改几个字而失效；只有整段被删除时笔记才随之删除。

### 10.3 编辑档的行为约定

- **富文本（段落）视图**：
  - 阅读高亮、下划线、划词译文标记可见，且可编辑；
  - 删除被标注的文字 → 该标注一起删除（与文本同生命周期）；
  - 段落整体删除 → 该段的高亮、下划线、划词译文、笔记一并删除；
  - 段落内局部改写 → 笔记保留（段落还在），字符级标注按偏移重算，越界部分裁掉并标"部分失效"。
- **源码视图**：
  - 不渲染任何阅读标注；
  - 在源码里删掉的文字会连带删掉对应标注数据；
  - 源码模式**无法新增标注**（不能把标注加回来），需回到富文本视图或阅读档。
- **分屏对照视图**：左源码（无标注）+ 右富文本（有标注），规则分别同上。

### 10.4 编辑档视图三态（本次要改的 UI）

现状：段落视图右上角是「收起源码 / 并排源码」布尔切换，只能"有源码"或"没源码"。

改为三态切换，默认**富文本**：

| 状态 | 内容 |
| --- | --- |
| 富文本 | 只显示块级可编辑预览（带阅读标注） |
| 源码 | 只显示 HTML 源码文本框 |
| 分屏对照 | 左源码、右富文本并排，滚动独立 |

落点：`EpubEditPanel.tsx` 段落视图 `.block-bar` 右侧把 `splitOpen: boolean` 改为 `blockView: 'rich' | 'source' | 'split'`；`setSplitOpen` 的 Ctrl+滚轮、自动重建预览、字号记忆等依赖点同步改为按视图状态判断。

### 10.5 锚点模型（据此修订 §5.2）

```ts
type AnnotationAnchor = {
  href: string
  blockIndex: number        // 必填：段落/标题级定位
  textHash: string          // 段落原文归一化 hash
  blockText: string         // 段落原文快照（用于改写后重算）
  range?: { start: number; end: number }  // 字符级标注：相对 blockText 的偏移
  quote?: { before: string; exact: string; after: string }
  state: 'ok' | 'partial' | 'orphan'
}
```

- `blockIndex + textHash` 定位段落；段落文字变化但未删除 → `partial`，按 `range` 与新旧文本对齐裁剪。
- 段落被删除 → `orphan`，标注移入"待处理"列表，由用户在标注面板确认删除或重新挂载。
- 纯 `range` 标注不允许跨 block。

### 10.6 导入/迁移旧标注

- 旧 localStorage 标注只有 CFI + 文本：迁移时按 CFI 定位到 block，补 `blockIndex/textHash/blockText`；
- 定位失败的保留为 `orphan`，不静默丢弃。
